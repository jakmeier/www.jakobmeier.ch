- WASM solves sandboxing on a per module basis. WASI on top gives access to the OS features. Docker sandboxes on the OS level, share a kernel but isolate filesystem, network, memory,and so on. They are complementary to the point where docker even started supporting wasm modules as docker containers.

## Introduction

## Wasm on the server

Why do we need a sandbox on the server? The main use case I want to explore
would be for compute platform providers. Think AWS, Azure, GCP and the various
tiers of cloud services they provide. If they colocate multiple clients on the
same hardware, sandboxing is absolutely necessary. You don't want other users to
access your data and ideally you also don't want their workload to influence
your workload. So we actually have at least two kinds of isolation requirements.
Data secrecy and performance isolation.


There is a plethora of isolation techniques deployed in modern systems. Let me
start with processes. Each process is confined to its own virtual memory space
and can only use system resources through system calls that are managed by the
operating system. The operating system thus is in full control and can isolate
multiple processes from each other almost perfectly. (Only *almost* because
side-channel attacks on the hardware level are a thing.)

Now, the way we developer write programs, we often assume full access to things
like the filesystem or the network. The operating system could limit access very
granularly, similar to how an app installed on your phone has to request
permission to access your files. If we specified exactly what capabilities out
software needs like mobile apps, perhaps service providers could run processes
of multiple users in the same operating system. But that is not how we run our
services on our Linux servers. Instead, we typically assume most of the POSIX
system calls to just work, whether we know about it or not. Indeed we typically
don't care about specific POSIX calls, we just use the standard library of our
language, like libc, to do the low-level work for us. This simplified view makes
programming easier and accessible to more people, which is a good thing.

However, with the communication to the operating system hidden from programmers,
we lose the ability to do sophisticated permissions on the operating system
level. Hence, compute platforms default to giving you full access to an entire
OS instance. To colocate multiple of these on the same hardware, they use
virtual machines (VMs). Starting up a VM takes seconds to minutes and the memory
overhead can easily be in the Gigabytes.

With that we have access to an entire OS and we have decent isolation from other
users on the same physical machine. But what if we want to run multiple
processes and isolate them from each other properly? Running a separate VM for
each process is unpractical. Again, we could use traditional process isolation
and configure OS level permissions manually but it's just too much work. That's
where Docker comes in.

Running a process inside Docker also gives developers a view as if they have a
full OS to themselves. But Docker isolates system resources such as the
filesystem or the network on the OS level. Compared to VMs, it can reuse the
same OS kernel for all containers. This can reduce startup time and memory
overhead by maybe an order of magnitude. As en example, an empty Debian Docker
image is only around 50MB and starts in less than a second. That overhead is
often negligible compared to the applications running inside.

With Docker, however, developers have to be explicit again about permissions. If
you want a file from outside to be accessible inside the Docker image, you have
to set it up in that way. Same goes for network ports. Docker just makes this
easier than doing it all manually on the OS level. Further, tools like
docker-compose can help to automate even the glue between Docker containers.

Okay, how does that relate to Wasm on the server? Believe it or not, there are
already 4 different ways of using Wasm on the server worth discussing and
probably that still doesn't cover the subject properly.

1) Run it as pure Wasm.
2) Run it through the Wasm System Interface (WASI)
3) Run it through one of many Wasm backend frameworks
4) Run it as a Docker container

### Pure Wasm on the Server

The purest form of Wasm is to compile to for `wasm32-unknown-unknown`, which makes
no assumptions on the runtime. Here is a complete example.

```toml
# Cargo.toml
[package]
name = "is-thirteen"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[dependencies]
```

```rust
// src/lib.rs
#[no_mangle]
pub fn is_thirteen(num: u32) -> bool {
    num == 13
}
```

As you can see, the example code is extremely simple. We just take a number as
input and return a boolean value whether it is equal to the number 13 or not.

Cargo can compile this into a portable and runtime agnostic wasm module.

```bash
$ cargo build --release --target wasm32-unknown-unknown
```

Now, using [wasmtime](https://wasmtime.dev/) as the runtime in this example, we
can execute this module.

```bash
$ wasmtime run is_thirteen.wasm --invoke is_thirteen 1
0
$ wasmtime run is_thirteen.wasm --invoke is_thirteen 12
0
$ wasmtime run is_thirteen.wasm --invoke is_thirteen 13
1
$ wasmtime run is_thirteen.wasm --invoke is_thirteen 14
0
```

I hope this makes sense so far, on a high level. But there is already a bunch of
magic happening that I want to explain.

A sandbox restricts access but also has to define a way to overcome
restrictions, on other word, it has to define how to communicate with what is
outside the sandbox. In this example, the input comes from outside the sandbox
and the result is returned to the outside world.

In the example above, the wasmtime CLI made a few assumptions for us. It took
the argument we gave it on the command line, which is a string, and converted to
a number. Then it pushed that on the virtual Wasm stack before calling the
`is_thirteen` function. After the function finished, it popped the return value,
which we defined to be a `bool` in Rust. This is then represented as `0` or `1`
in a string output we see on the command line.

These steps are not part of the Wasm standard. It's a choice of the CLI how to
make running pure Wasm modules somewhat useful. To understand better what is
really going on under the hood, we can inspect the Wasm module with `wasm2wat`
from the [The WebAssembly Binary Toolkit](https://github.com/WebAssembly/wabt).

```bash
$ wasm2wat ./target//wasm32-unknown-unknown/release/is_thirteen.wasm
```

```wat
(module
  (type (;0;) (func (param i32) (result i32)))
  (func $is_thirteen (type 0) (param i32) (result i32)
    local.get 0
    i32.const 13
    i32.eq)
  (table (;0;) 1 1 funcref)
  (memory (;0;) 16)
  (global $__stack_pointer (mut i32) (i32.const 1048576))
  (global (;1;) i32 (i32.const 1048576))
  (global (;2;) i32 (i32.const 1048576))
  (export "memory" (memory 0))
  (export "is_thirteen" (func $is_thirteen))
  (export "__data_end" (global 1))
  (export "__heap_base" (global 2)))
```

This is the code produced by `cargo`, without knowing anything about the runtime
we are going to use to run it.

The module is only 15 lines long. Four of them are the actual function, which
reads parameter 0 and compares it to the constant 13. The return is implicit by
keeping the result on the stack.

```wat
(type (;0;) (func (param i32) (result i32)))
(func $is_thirteen (type 0) (param i32) (result i32)
   local.get 0
   i32.const 13
   i32.eq)
```

Before the function, the type is defined as a function that takes one parameter
and returns a result. Since this is the first definition in the module, it is
implicitly type 0 for future references. For convenience, the `wasm2wat` command
also puts that into a comment (`(;0;)`). (Yes, wat inline comments start with
`(;` and end with `;)`).

Did you note how `i32` is used in the binary despite `u32` in the code? Well,
Wasm doesn't have a native `u32` type. So on the binary level, it uses `i32`.
Any `u32` value can be encoded as a `i32` and thanks to [Two's
complement](https://en.wikipedia.org/wiki/Two%27s_complement) encoding,
arithmetic operations are equivalent. That's good enough if the caller knows
how to encode values. But does wasmtime know it? Let's try.

```
$ wasmtime run is_thirteen.wasm --invoke is_thirteen 2147483647
0
$ wasmtime run is_thirteen.wasm --invoke is_thirteen 2147483648
Error: failed to run main module `is_thirteen.wasm`
Caused by:
    number too large to fit in target type
```

Oh, oh. If we try to pass a number higher than `i32::MAX = 2147483647`, wasmtime
fails to encode it. This makes sense, given the Wasm module defines the
parameter as `i32` and there is no way for wasmtime to know that our original
code wanted a `u32`. That shows how the glue between a portable app and a
runtime is important.

What else is exposed by the module for the runtime?

```
(export "memory" (memory 0))
(export "is_thirteen" (func $is_thirteen))
(export "__data_end" (global 1))
(export "__heap_base" (global 2)))
```

The module has 4 export entries. One of them is our function we just looked at,
exported with the name "is_thirteen". Before that is a memory region named
"memory", which internally references memory number 0. This was previously
defined to hold 16 pages of 64 KiB each, hence 1 MiB in total.

```wat
(memory (;0;) 16)
```

This tells the runtime any code inside will only access memory addresses 0 to 1
MiB. The runtime can allocate it accordingly.

The last two exports are pointers into the memory called `__data_end` and
`__heap_base`. This helps the runtime understand how the module organizes its
memory internally.

```
(global (;1;) i32 (i32.const 1048576))
(global (;2;) i32 (i32.const 1048576))
```

Both are set to `1048576`, exactly at 1 MiB. With `__data_end` set to this
value, it means the module has the region from 0 to 1MiB for the data section.
If we had constant strings in our code, they would show up in the data section.

At the exact same address `1048576`, the heap starts, meaning everything
afterwards is dynamically managed memory. Since the entire memory region is only
1 MiB, we can conclude the module has no heap in this case.

If there was some space between  `__data_end` and `__heap_base`, this could be
used as a stack by the Wasm code. Not the stack of the Wasm virtual stack
machine as I explained in [Fundamentals of WebAssembly]({{ url00 }}) but the
stack where your programming language can put data temporarily, without a
dynamic memory allocator. But anyway, this example has no such stack since the
code is simple enough.

Okay, the module exposes its internal memory details. But why? You might have
guessed it, it has to do with sandboxing.

First, defining the memory region allows the runtime to map Wasm addresses to
host virtual addresses efficiently. In Wasm, there might be a pointer of value
8. This is relative to the Wasm module and another module in the same runtime
could also have an address of 8 that references something completely different.
The runtime has translates Wasm addresses of a module to valid native pointers.
Ideally, without allowing sandbox escapes.

So here is what happens, for example. The runtime allocates a 1 MiB memory
region for the data section of the Wasm module. Let's say that region has a
native address of `0xffff_0000_0000_0000`. An interpreter would now add
`0xffff_0000_0000_0000` to each data section access to do the address mapping.

A more efficient runtime can avoid doing this work on each memory access. It can
translate all addresses during compilation of the Wasm to native code. Hence,
this add happens during module loading / compilation, not during during execution.

For the data section, which is a static size during execution, this works
well-enough. The stack and the heap, however, can usually grow dynamically.
Ideally, the runtime should start with a small allocation and be ready to
dynamically increase it as necessary. That's one of the reasons why it can be
good for the runtime to know which addresses are considered to be on the heap by
the program.

These intricate details of how memory management is shared between runtime and
program needs to be considered when building a sandbox. Other runtime, like
Java, decided to put everything on the runtime and dictate the usage of a
garbage collector. Wasm tries to dictate as little as possible.

So much about this pure Wasm situation. It has very tight sandboxing. So much so
that it's hard to show a more useful example of it. If we wanted to do something
interesting, like even just printing something to the console, we would need to
switch gears and invoke wasmtime as a library from code, so that we can define
imports like we did in the JS example. That's for another day. But if we are
willing to make use of more standards than just pure Wasm, then there are ready
available tools to make things easier.

### WASI on the Server

The most vanilla layer of abstraction on top of pure Wasm, for the backend,
would be the Wasm System Interface (WASI). Like POSIX system calls, it is an API
to gives the program access to system resources. And if you are using emscripten
(yes, it works on the backend, too) then you also have the standard library to
access it conveniently from you programming language of choice.

Through WASI, you may access system resources like files or the network. WASI
support among Wasm runtimes is great, generally speaking, but be warned that
things are still moving in this area.

Like Wasm, WASI is a standard developed by the W3C. Wasm has had it's 1.0
release a while ago and all major browsers support it. WASI builds on top of it
and naturally lags behind a bit regarding stability.

The first WASI standard preview was floating around for a couple of years and
has been implemented by multiple Wasm runtimes. Today, what came out of it is
known as WASI 0.1. Despite the number indicating instability, it works well
enough that it is used in production.

There is also WASI 0.2, which I believe is supposed to replace WASI 0.1. But it
was only released in February 2024, so I wouldn't quite call WASI 0.1
deprecated, yet.

With WASI, we can now create a more interesting example. Let's create a Wasm
component that validates a signed message using a certificate stored in a file.

```toml
# Cargo.toml
[package]
name = "wasm-signature-checker"
version = "0.1.0"
edition = "2021"

[dependencies]
ed25519-compact = "2"
hex = "0.4"
anyhow = "1"
```

```rust
// main.rs
use ed25519_compact::{PublicKey, Signature};

fn main() -> anyhow::Result<()> {
    println!("> Wasm signature verifier, featuring WASI.");
    println!("> Please enter the message text.");
    let message = read_line()?;

    println!("> Please enter the signature in hex encoding.");
    let hex_input = read_line()?;
    let binary_input = hex::decode(hex_input.clone())?;
    let signature = Signature::from_slice(&binary_input)?;

    println!("> Please enter the path to the certificate.");
    let path = read_line()?;
    let pk_vec = std::fs::read(&path)?;
    let pk_array: [u8; 32] = pk_vec.try_into().unwrap();
    let pk = PublicKey::new(pk_array);

    println!(">");
    println!("> Verifying ");
    println!(">           {message}");
    println!(">           {hex_input}");
    println!(">           {path}");
    match pk.verify(message, &signature) {
        Ok(()) => println!("valid"),
        Err(_) => println!("invalid"),
    }
    Ok(())
}

/// Read a line from stdin and remove trailing whitespace, such as \n
fn read_line() -> Result<String, anyhow::Error> {
    let mut line = String::new();
    std::io::stdin().read_line(&mut line)?;
    line.truncate(line.trim().len());
    Ok(line)
}
```

```bash
# set up certificate in a new directory
mkdir guest_dir
echo "D0A6947EF7BDA615D38B43A896AE6EA6FDE87F98729C18B6D9AB447051B0E7A0" | xxd -r -p > ./guest_dir/my_pk.cert
```

The code isn't all that important, just note how I'm using the Rust standard
library to read from standard input and read a file from a path. Also,
`println!` prints to the standard output.

None of this would be defined in pure Wasm. But when I compile it for `--target
wasm32-wasi`, it all gets mapped to the WASI interface.

```bash
cargo build --release --target wasm32-wasi
cp ./target/wasm32-wasi/release/wasm-signature-checker.wasm ./
```

Finally, we can run the code with wasmtime again, this time in interactively.


Probably the most important part here is how we have to give explicit permission
to read the file `./guest_dir/my_pk.cert`. By adding `--dir ./guest_dir::/` as
an argument, I mapped `./guest_dir` to `/` inside the filesystem the Wasm
runtime exposes. Anything outside the directory is unaccessible, as I can
demonstrate by trying to access for example `../secret_key`.

```bash
# Demonstrate sandboxing in WASI
# ...
$ wasmtime wasm-signature-checker.wasm --dir ./guest_dir::/
> Please enter the path to the certificate.
../secret_key
Error: Operation not permitted (os error 63)
```

As you can see, the sandboxing model of WASI is similar to Docker. By default,
no access. But all the tools are available to quickly give access to specific
parts of the system.

If instead I run the example as a native binary and not as a Wasm module, the
program has access to anything my current user has access to...

```bash
# Demonstrate non-sandboxing in native
$ cargo run
# ...
> Please enter the path to the certificate.
/home/jakmeier/.ssh/id_ed25519.pub
thread 'main' panicked at src/main.rs:16:48:

```

In the example above, running this on my dev machine, my real ed25519 public key
was printed out. It wouldn't work with my private key, since I have the usual

again, relying on specific configurations on the OS level for isolation of

### Docker integration of Wasm

To round up the Wasm on the backend part, let's talk about Wasm and Docker.

Of course, you could always put a Wasm runtime inside a Docker container, copy a
Wasm module inside, and execute it like that. I wouldn't blame you, it gives you
the benefit of being integrated with existing tooling around Docker containers.

But in this way, you give up on the fast startup times of Was, the small memory
footprint, and even portability is dampened (Dockerfiles differ by CPU
architectures).

A better way to integrate Wasm modules inside your Docker engine is with "Wasm
workloads" as they are currently called in the
[official documentation](https://docs.docker.com/desktop/wasm/).

You can define a Wasm workload in a dockerfile by starting with a completely
empty image and only copying in the Wasm to execute.

```Dockerfile
FROM scratch
COPY --from=build /build/hello_world.wasm /hello_world.wasm
ENTRYPOINT [ "/hello_world.wasm" ]
```

Like any other dockerfile, you can push this to a Docker image repository and
run it with the usual commands. But when you run it, you have to specify which
runtime you want. For example, to pick wasmtime:

```bash
docker run \
  --runtime=io.containerd.wasmtime.v1 \
  --platform=wasi/wasm \
  secondstate/rust-example-hello
```

That's pretty cool, right? We get the familiar Docker tooling and the
well-tested sandboxing properties of it. But you applications can be really
small, easily below 1 MB for simple applications. And startup times can be a few
milliseconds.

## Wasm in blockchains

In this last section, I will talk about how Wasm sandboxing is useful for blockchains.

Similarly to WASI based Wasm compute platforms on centralized servers, there are
a bunch of decentralized Wasm compute platforms that are based on blockchain
technology. The reason to decentralize it is, of course, to make it anonymous
and permissionless. In other words, anyone who somehow got access to the
blockchains native currency can just use the services. No email or credit cards
needed to sign up. No risk of censorship or locking you in for an expensive
enterprise business plan in the future. Just a platform open to everybody with
all the rules defined in code.

Whether you think these platforms are valuable to humanity or not doesn't really
matter for this discussion. I am no here to convince ou of either opinion. I
just gave you the reasons why people decided to create such platform and I will
now proceed to talk about why Wasm has been chosen by several projects in
this space.

First we need a unpack what a smart contract blockchain is. For our purpose,
let's just say it is global state shared through a distributed protocol. Among
all existing blockchains, some are smart contract blockchains which allow to
execute small programs on top of the global state, rather than just adding
static state to it. Naming these programs "smart contract" is a questionable
choice if you ask me but that is the most commonly used term.

Smart contract blockchains typically consist of hundreds of machines across the
globe. All those machines execute the same code that users submit. Then they all
compare the results and commit it to the chain if everyone got the same result.
The duplicated work and the comparison round is necessary because everyone in
the system is anonymous and any individual participant cannot be trusted to
compute and report the results truthfully.

When the developers behind the blockchains decided what runtime to use for the
smart contracts, some of them decided to create a new runtime with an
accompanying new programming language from scratch. The most famous example
would be the
[Ethereum Virtual Machine (EVM)](https://ethereum.org/pcm/developers/docs/evm/) with
the [Solidity](https://soliditylang.org/) programming language created for it.

Other projects did not want to reinvent the wheel. They are already inventing
plenty of new wheel shapes, maybe they can at least use existing programming
language, compilers and runtimes, right? At least some new founders saw it this
way and either flocked towards the now established ecosystem around the EVM or
they decided to use Wasm. Among the top 50 crypto tokens by market cap today, I
found four ecosystems using a Wasm runtime in their nodes. Namely Polkadot, Near
Protocol, Internet Computer, and Cosmos. (Several other projects provide the
tooling to execute Wasm smart contracts, too, but as far as I can tell none of
them actually include a Wasm runtime, hence they are not directly relevant in
this article.)

They could have used any existing language, really. Something like Java wouldn't
be to bad a choice. Heck, they could even allow submitting Dockerfiles to the
chain to download and execute pretty much anything on chain. But using Wasm has
its benefits.

Again, the main reasons for Wasm are performance, portability, and security.
Especially the fast startup times are important. It reduces the overhead per
smart contract invocation, and hence the cost charged to users. Furthermore, it
keeps latency down, which is one of the pain points of interactive web3 apps.

The sandboxing, however, I find most interesting personally. You see, security
has a catch-all term that often means privacy, secrecy, or a bunch of other
things.

In the case of blockchains, everything executed is public by design, hence there
are no secrets to reveal and no private information of users to protect. Hence,
it would not really matter if different smart contracts could somehow access the
data of other smart contracts. It might even be desired for cross-contract
interaction.


Execution sandboxing security, in blockchains, mostly comes down to protecting
the host system. A piece of untrusted code could try to escape the sandbox and
compromise the host system. Another potential attack would be to use more
resources than has been paid for.

This last problem is very blockchain specific. What should a runtime do when a
user submits code like this:

```rust
// simple infinite loop
loop {}
```

Usually, a compute platform can just let code run until a certain amount of time
has passed. Then they stop the program and return an error to the user, telling them
that they ran out of credits, or something along those lines.

But interrupting a system after a fixed amount of time is non-deterministic. Of
the many nodes replicating the same work, some might be able to just finish a
complicated piece of code, while other nodes with weaker hardware run into the
timeout. Now the nodes struggle to agree on the result, some will say the
execution failed while others will say it succeeded.

The solution is to keep counting how many operations are executed and interrupt
after a fixed number, making it deterministic across hardware. Some blockchains
measure this in virtual gas which needs to be purchased with the chain's native
token. But the idea is the same.

But this requires counting of instructions, which is not easy to do without too
much overhead. I mean, sure, modern CPUs always include hardware performance
counters for things like "number of retired instructions" or something similar.
Those could be used to count instructions at no extra cost. But this wouldn't be
consistent across different hardware.

So then, if we need a software solution, Wasm is a great choice because it only
has structured control flow. In other words, there are no `goto ADDRESS`  or
similar instructions. This severely limits the possible jump targets.
In Wasm, jumps only happen to the start and end of a `loop`, to start and end of `if/else`
statements, and for function calls / return statements.

All code blocks with non-control flow instructions cannot be jumped into, there
are no valid jump targets, as it would be the case in many other binary formats,
including Java byte code.

Why is this important? Because it allows a simplified way of counting
instructions. Instead of increasing a counter between every line, we can
increase the counter once per sequence of non-controlflow instructions.

Adding this sort of accounting logic isn't exactly trivial. But it certainly is

Wrapping up the discussion on protecting against users using more resources than
they can pay, Wasm blockchains do this kind of instruction counting and
conceptually subtract a bit of the users money before every block of
instructions. Then, if the value reserve money/gas reaches zero, execution is
halted, which is going to be at the exact same position on all nodes
participating in the distributed systems. Some might take longer than others to
reach this point but the final result is deterministic.

Puh, so much about why the design principles of Wasm are a great fit for
blockchain usage. That's a form of resource isolation. But what about the
protection of the host from getting compromised?

Previously, I mentioned that no secrets are inside the wasm runtime since the
entire state is fully public anways. On the host, however, there are important
secrets to protect.

As the name of crypto-currency suggests, all important messages are
cryptographically signed and verified. And the private key for signing has to be
stored somewhere accessible to the node. Now, what if I tell you that some of
these projects run the wasm runtime with untrusted code in the same process as
the trusted code that signs those messages?

Yes, that's exactly what's happening. Some projects completely rely on Wasm
sandboxing to protect those keys. On one hand, that's pretty wild from a
security point of view. A bug in the runtime code could quickly lead to a fully
compromised network. But on the other hand, even the Wasm type-system with
structure control flow and checked memory accesses can prevents several classes
of bugs, as long as the typechecking code is correct. Also, the compiler in
these runtimes is much simpler compared to what you would find in a JVM, for
example.

Putting each smart contract execution into a separate process that doesn't even
have access to signing keys could give better security, of course. But starting
a new process every time would add non-trivial latency. In Near Protocol, the
system I worked on myself, we allocate only 780 μs for starting a smart
contract. Linux can easily take longer than a millisecond for a `fork() + exec()`
call.

I guess one could have a pool of reusable processes, or even just use a single
process running just the Wasm runtime that receives the code to run over inter
process communication channels. That would add less overhead but it still
wouldn't be free. 

Instead, the Wasm runtime in Near Protocol mostly relies on the Wasm security
model. The only real isolation on top of that is memory mapping. This involves
standard practices, like only marking the memory regions with the code as
executable, and Wasm specific tricks. Since Wasm uses 32-bit addresses, it can
only directly address 4 GB of memory. This means, we can reserve a region of 4
GB virtual address space after the Wasm memory start. The Wasm program has
physically no way of even specifying a memory address outside of that.

Is this perfect security? Of course not, nothing ever is. Sandboxes have been
escaped many times. Wasm is not magically not invulnerable to programmer
mistakes. If you need an example for a Wasm runtime escape in V8, take a look at
["A Deep Dive into V8 Sandbox Escape Technique Used in In-The-Wild Exploit"](https://blog.theori.io/a-deep-dive-into-v8-sandbox-escape-technique-used-in-in-the-wild-exploit-d5dcf30681d4)
by Theori Vulnerability Research.

But personally I think the security guarantees are good enough in the case of
Near Protocol. We should keep in mind that the Wasm runtime in Near Protocol
uses a very simple single-pass compiler, no Just-In-Time compilation, and
battle-tested Wasm code validation libraries.

Keeping it simple like that, the amount of code with potential vulnerabilities
is relatively small. Isolation layers could help but it also increases the
amount of code that is responsible for isolating properties. I would rather have
a small piece of hardened code that several people in the team know really well
and where everybody is on edge to prevent bugs in it at all costs, instead of
security-in-depth with a false sense of security. This way, the team can set up
continuous fuzzing and employ extra rounds of code reviews for the critical
code.

Particular security assumptions:
- Typically, all the state is public. No secrets to steal from other Wasm processes.
- But the machine has miner/validator keys, often worth millions.
- However, blockchains often duplicate work to double-check the validity, unless ZK is used. Scary for denial of service.
- Simply putting a time and memory limit on a process won't work. Not deterministic, so the system won't agree on the exact result.
- Wasm with structured control flow makes it somewhat efficient to limit the executed instructions exactly with a hard limit.
   - the same could be done with cpu instruction counters using performance monitoring counters (PMC) but you would be bound by cpu architecture
   - you could instrument Java or .NET to do this kind of counting too
- Fast up times and small binary sizes means millions of people can share the same resource and have cheap function calls (cheap and public FaaS)
- It should be easy to add custom functions, like send money
